THE CONTEXT

Trainix is an enterprise platform that helps pharma and clinical teams manage SOPs, assessments, training events and audit trails in one place.

Admins run the whole organisation, managers look after their department, and employees see only their own training. I owned the design end to end and built the front end myself with an AI coding agent, while a backend developer built the API. Before designing any screens, I built the system all three of us would build on.

Design systemFigma libraryFront-end buildAccessibility

DESIGN SYSTEMS IN THE AI ERA

AI doesn’t ask. It fills every gap with its own taste.

Today a lot of front-end code is written by AI agents. That changes what a design system is for: it isn’t only a library for people, it’s the rulebook an agent reads before it writes a line of code. This project is how I make a system consistent enough to work with AI.

1.

AI agents need a source of truth

An AI coding agent builds fast, but only as consistently as the rules it can read. The design system is that rulebook.

2.

No rules? AI writes its own

When a rule is missing, the AI doesn’t ask. It fills the gap with its own taste, a little differently every time.

3.

The system is the brief

Tokens, component specs and written rules become the prompt behind every screen, so people and AI build the same way.

DISCOVERY

UX problems identified

What actually happened when I built screens with an AI agent before the system existed: mediocre, inconsistent design, a little different every time.

Asked for a table, the AI invented a new grey, a new radius and a purple badge
Two screens built a day apart came back with two different button styles
Without rules, the AI fell back on generic “AI slop”: gradients, oversized cards and emoji icons
It hardcoded colour values instead of tokens, so one brand change meant hunting through files
Loading, empty and error states were skipped unless asked for every single time
Status shown by colour alone, and generic “Submit” buttons everywhere
The same colour had three names across Figma, the UI kit and code
Rules lived in my head, not anywhere an AI could read

THE RESEARCH

What tools people trust with dense data get right

I studied Linear, Stripe, Zoho, Deel, Remote, Apollo and Mixpanel.

1.

Quiet chrome, loud content

The sidebar fades into the page so the data does the talking.

2.

Restraint with colour

Brand blue only for the main action, links and focus. Red only for errors.

3.

Calm tables

No zebra stripes or vertical lines. The person first, one place for row actions.

4.

Every state designed

Skeletons while loading, an action when empty, a retry on error.

WHO IT’S FOR

Three builders, one language.
A designer, a developer and an AI assistant.

Who uses the system

The designer draws every screen from the Figma library.

The developer connects screens to the Django backend and needs names that match.

The AI coding assistant builds components and screens, and needs rules it can read.

“Which grey is the border, and what is it called in code?”

“Is there already a component for this, or do I make one?”

“What should this look like while it loads, or when it’s empty?”

THE RULES

Rules the system never bends

Some rules come from the product, some from accessibility. Both are written into the system, so a person and an AI agent follow them the same way.

Product rules and accessibility rules

Records stay read-only

Training records, audit logs and old SOP versions get no edit or delete buttons.

No compliance claims

The interface never says “21 CFR Part 11 compliant” or “GxP compliant”.

The server decides

Scores and pass/fail come from the backend. The interface only shows them.

Visible focus everywhere

Every interactive part shows a focus ring on keyboard focus.

Status is never colour alone

Every badge and alert carries a word or an icon.

Every input is labelled

Visible labels, hints below, errors that say how to fix them.

Two tiers of tokens

Components never touch raw colours. They use semantic tokens named by their job, which point to one primitive palette.

1.

Primitive

The raw palette: blue/700, neutral/300. Never used directly in components.

2.

Semantic token

Named by its job: bg-brand-solid, text-tertiary. 51 of them, the same in Figma and code.

3.

Component

The Primary button reads bg-brand-solid. Change the primitive once and every component follows.

KEY DECISIONS

Decisions that shaped the system

1.

Figma names are code names

bg-brand-solid in Figma is bg-brand-solid in Tailwind. Handoff became matching words.

ACCESSIBILITY

The system checks itself

A WCAG contrast audit runs on every token change. It flagged three real issues in the Trainix colours, each with a one-step fix.

  • Warning text · 3.56:1

    Orange text on white sat below the 4.5:1 small text needs. Fix: one shade darker.

  • Warning badge · about 3.3:1

    Orange on its pale tint failed too. The audit suggests the smallest change that passes.

  • Error badge · about 4.0:1

    Close, but under AA. One step darker passes with no visible change to the look.

IMPACT

What the system delivers

13 principles · 8 AI rules

Each with a Do and a Don’t, so people and the AI build the same way

LEARNINGS

A design system is a promise, kept in two places

  • A defined system is mandatory when working with AI.

    It’s like working with a team, except this team never asks. It applies its own knowledge, so every rule I didn’t write became a guess.

  • Design the boring states first.

    Loading, empty and error screens are where trust is won or lost in a compliance tool.

  • Rules scale better than reviews.

    Writing them for an AI agent made them clearer for people too.
